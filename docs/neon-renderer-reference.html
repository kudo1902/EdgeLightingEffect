Spaces and sign conventions

  • Local space is what vPos carries: pixels, origin at the rectangle's centre, +Y up. All SDF work happens here.
  • d is the signed rounded-box distance: negative inside, 0 on the outline, positive outside. ad = abs(d).
  • t / sPos / si are perimeter positions in [0, 1), measured by arc length from the start of the top edge, in the configured winding direction.
  • Every length uniform reaching the shader is in pixels - full-resolution pixels in neon.frag, FBO pixels in neon-optimized.frag. That distinction is the whole of section 14.
  • Output is premultiplied alpha, paired with glBlendFunc(GL_ONE, GL_ONE_MINUS_SRC_ALPHA).
Single source of truth neon-tuning.h is #define-based rather than constexpr because it is compiled as both GLSL and C++. GLSL ES 3.00 has no constexpr and rejects the f float suffix, so plain macros are the only form valid in both languages. The file is injected verbatim via @NEON_TUNING@, so a shader constant and its C++ counterpart cannot drift.

03 Geometry and the SDF

The rounded-box distance

float sdRoundBox(vec2 p, vec2 b, float r) {
    vec2 q = abs(p) - b + r;
    return min(max(q.x, q.y), 0.0) + length(max(q, 0.0)) - r;
}

p is the fragment in local space, b the half-extents, r the corner radius. Term by term:

TermDoes
abs(p)Folds the plane into one quadrant. The shape is symmetric, so one quadrant of arithmetic covers all four.
- b + rShifts into the frame of the smaller, sharp-cornered box of half-extent b - r. A rounded rectangle is exactly that box with a disc of radius r rolled around it.
length(max(q, 0.0))Exterior case: clamping negatives to zero projects onto the smaller box, giving the straight-line distance to it.
min(max(q.x, q.y), 0.0)Interior case: distance to the nearest wall is the larger (least negative) of the two axis distances.
- rRecovers the rounded shape by subtracting the rolled disc's radius.

The result is an exact Euclidean distance, not a bound or an approximation. Two consequences the rest of the shader relies on:

  • d is directly comparable against pixel-valued settings (lineWidth, glowRadius, the cutoffs) with no conversion.
  • Every level set of d is itself a rounded rectangle with radius r + d, so corners are never a special case. This is why glowSide is a single comparison against sign(d) and why a 40 px glow follows a corner at the correct width.

Band boundary distances

The cutoff band needs two more signed distances. dIn >= 0 means "past the inside cutoff"; dOut <= 0 means "within the outside cutoff".

float bandOuterDistance(vec2 p, float d, vec2 halfSize, float r, float cut) {
    if (r > 1e-4) { return d - cut; }          // parallel curve: uniform width
    vec2 b = halfSize + vec2(cut);
    return sdRoundBox(p, b, 0.0);              // per-axis: keeps the corner square
}
float bandInnerDistance(float d, float cut) { return d + cut; }

The r == 0 branch exists because the parallel curve of a sharp corner is an arc of radius cut. Taking d - cut there would round the outer corners of a rectangle the designer explicitly asked to be square, and the opaque fill (drawn on a fullscreen quad with no such rounding) would then bulge black past the glow at each corner. Offsetting per-axis instead keeps the corner square at the cost of the band being about 1.41x wider measured diagonally across it. A uniform width and a square outer corner cannot both hold at a sharp corner.

Both functions no-op for disabled cutoffs: the sentinel drives dIn hugely positive and dOut hugely negative, so both masks evaluate to 1.

04 Perimeter inversion

Turning a fragment position back into an arc-length parameter. This is the fiddliest function in the shader and the one most likely to be got wrong by a well-meaning edit.

Step 1: nearest point on the outline

vec2  b  = vec2(halfWs, halfHs);   // the smaller, sharp-cornered box
vec2  c  = clamp(p, -b, b);        // nearest point on that box
vec2  d  = p - c;
float dl = length(d);
if (dl > 1e-6) { cp = c + d * (r / dl); }   // push out by r -> on the outline
else           { /* project along the dominant axis, see below */ }

This is the distance formula run backwards: instead of returning how far the nearest point is, it returns where it is. The dl <= 1e-6 branch handles fragments strictly inside the inner box, where the direction is degenerate; it projects along whichever axis is closer to its wall:

vec2  e  = b - abs(p);
float sx = (p.x >= 0.0) ? 1.0 : -1.0;
float sy = (p.y >= 0.0) ? 1.0 : -1.0;
cp = (e.x < e.y) ? vec2(sx * halfW, p.y) : vec2(p.x, sy * halfH);

Step 2: which of the eight pieces

With ax = abs(cp.x) and ay = abs(cp.y), a chain of comparisons classifies cp into a canonical id numbered in clockwise order, and computes u, the traversal progress across that piece measured clockwise.

Step 3: cumulative base, then divide

With ws = width - 2r, hs = height - 2r, arcLen = PI * r / 2 and peri = 2ws + 2hs + 4arcLen, the piece id selects a cumulative base. The two windings use different tables and the counter-clockwise one mirrors the progress to 1 - u.

Note that t = 0 sits at the left end of the top edge for clockwise winding, which is where the top-left corner arc finishes, and at the bottom end of the left edge for counter-clockwise.

Why geometric and not sampled An earlier version estimated a fragment's position as a proximity-weighted circular mean of the nearby loop samples' phases. Near a corner those phases wrap through 2pi straight into the start of the ring, so the mean collapsed the whole corner curve to roughly 0 and lit corners that an arc starting at 0 should have left dark. The geometric inverse is exact everywhere. It is also what makes CPU-authored positions agree with the shader: GeometryUtils::GetPointOnRectangle is the forward map of exactly these tables.
If you change this Four places must move together: perimeterPosition in neon.frag, its copy in neon-optimized.frag, GeometryUtils::GetPointOnRectangle (and its Detail::GetPointOnRectCW / CCW helpers), and GetSunFragPosition, which places the lens-flare sun in the same parameter space. A mismatch shows up as arcs that do not line up with where the UI says they are.

05 The filament

A generalized-Gaussian profile in ad:

float halfWidth = uLineWidth * 0.5;
float sigma     = max(halfWidth, FILAMENT_MIN_HALF_WIDTH);
float N         = 2.0 * max(uFilamentFalloff, 1e-3);
float core      = exp2(-pow(ad / sigma, N));

Written with exp2 rather than exp so that sigma is the half-brightness radius by construction: core = 0.5 exactly at ad = sigma, for any N. Peak is always exactly 1.0 at ad = 0. The exponent maps as:

filamentFalloffNShape
0.51Laplace. Heavy tails, smooth peak.
1.02Gaussian. The default; no power-law tail, so the line reads clean with no far bleed.
2.04Platykurtic. Flatter top, sharper shoulder.
5.010Near-rectangular.

Reach, and the pedestal

The profile has no finite support, so both the shader and the CPU need an agreed cutoff distance. Solving core * FILAMENT_GAIN < FILAMENT_CUTOFF gives

reachSigmas = clamp(pow(log2(FILAMENT_GAIN / FILAMENT_CUTOFF), 1.0 / N),
                    FILAMENT_REACH_MIN_SIGMAS, FILAMENT_REACH_MAX_SIGMAS);

This is emphatically not a constant, because the tail length depends on N:

filamentFalloff2.01.00.50.30.2
reach, in sigmas1.93.512.667.8558

It diverges as filamentFalloff -> 0. A fixed 12 (calibrated at falloff 0.5) badly under-sized the low end: the interior is unbounded because the quad always covers it, so a soft filament flooded inward while the exterior was chopped at 12 sigmas. That asymmetry was the "no outer glow at glowRadius 0" report. FILAMENT_REACH_MAX_SIGMAS bounds the fill cost where the formula diverges.

The core is then pedestal-subtracted so it reaches exactly zero at that reach, and renormalised so the peak stays 1.0:

float corePed = exp2(-pow(reachSigmas, N));
core = max(core - corePed, 0.0) / max(1.0 - corePed, 1e-6);

Where the reach formula is honoured the pedestal is about 1.7e-4 and invisible. Where MAX_SIGMAS clamps it, this is what makes the glow end smoothly and, crucially, symmetrically - without it the interior keeps its full tail while the exterior is cut at the quad edge.

The zero-width gate

float lineGate = clamp(uLineWidth / (FILAMENT_MIN_HALF_WIDTH * 2.0), 0.0, 1.0);

sigma is floored at FILAMENT_MIN_HALF_WIDTH, so lineWidth = 0 would otherwise render a half-pixel bright dot rather than nothing. The gate fades the whole filament out over lineWidth in [0, 1], making 0 mean "no line".

06 Halo and bloom

Both were once sums over the 128 perimeter samples. Both are now closed forms in ad alone, and that single change is what made the effect geometry-independent.

The derivation

Take a straight emitting line of unit density, a fragment at perpendicular distance ad, and let x run along the line. The old loop summed a kernel over x at spacing perimeter / 128. Letting the spacing go to zero turns each sum into an integral with an exact answer:

halo:   ∫ (x² + A²)^-3/2 dx = 2 / A²     with A² = ad² + kh²
bloom:  ∫ 1 / (x² + A²)  dx = π / A       with A  = sqrt(ad² + bw²)

Substituted back with the emitter widths, those are exactly the two lines in the shader:

float kh    = max(uGlowRadius,                       EMISSION_MIN_WIDTH);
float bw    = max(uGlowRadius * BLOOM_REACH_TO_GLOW, EMISSION_MIN_WIDTH);
float halo  = HALO_NORM_FACTOR  * 2.0 * kh * kh / (ad * ad + kh * kh);
float bloom = BLOOM_NORM_FACTOR * PI * bw / sqrt(ad * ad + bw * bw);
LayerWidthFalls off asPeak at ad = 0Half brightness at
Halokh = glowRadius1 / ad²0.86ad = kh
Bloombw = glowRadius * 61 / ad1.005ad = bw * sqrt(3)

The peaks are HALO_NORM_FACTOR * 2 = 0.86 and BLOOM_NORM_FACTOR * PI = 1.005, identical to what the sums produced. That is the point of expressing the norms this way: the calibration constants kept their meaning and nothing had to be re-tuned by eye when the sums were replaced.

What the rewrite fixed

The gather had to floor its kernel at a multiple of sampleSpacing to stop 128 discrete samples beading into dots, and sampleSpacing is perimeter / 128. So halo width, and through the gate its brightness, both tracked the rectangle size, and glowRadius did nothing at all until it exceeded that floor - roughly 56 px on a 1920x1080 rect, which is most of its usable range. An analytic profile cannot bead at any radius, so no floor is needed.

One honest regression On the concave side of a corner the old sum picked up light from both incident edges, so corners ran hotter - measured at about 40% at 25 px inside a 40 px corner with glowRadius 25. A profile built from the distance to the single nearest point cannot reproduce that. The gap closes as glowRadius shrinks relative to cornerRadius, and is nil at cornerRadius 0.

The bloom pedestal

The 1/ad tail is heavy: at the draw quad's edge it is still around 10% of peak, so without correction the quad has to be enormous or the emission gets visibly chopped. The shader recomputes the CPU's uncapped quad-sizing formula and subtracts a pedestal sized to land the bloom at exactly zero there:

float reach     = max(uGlowRadius * EARLY_OUT_RADIUS_FACTOR *
                      (1.0 + uBloomStrength * uIntensity),
                      sigma * reachSigmas);
float bloomPeak = BLOOM_NORM_FACTOR * PI;
float bloomPed  = BLOOM_NORM_FACTOR * PI * bw / sqrt(reach * reach + bw * bw);
bloom = max(bloom - bloomPed, 0.0) * (bloomPeak / max(bloomPeak - bloomPed, 1e-6));

Two subtleties. It uses the uncapped reach, a pure function of glowRadius, bloomStrength and intensity, so the pedestal stays size-invariant even where the outside cutoff clamps the actual quad smaller; feeding it the clamped margin would subtract a huge pedestal and dim the whole band. And the second term of the max is the same filament-reach floor setupGeometry applies, without which the two disagree at small glowRadius and reach hits 0 at glowRadius 0, making the pedestal subtract the entire bloom.

The halo needs no pedestal: falling as 1/ad², at the same distance it is about 2e-4 of peak, already invisible.

The emission gate

float glowGate = clamp(uGlowRadius / GLOW_GATE_FADE_PX, 0.0, 1.0);

glowRadius = 0 must read as "filament only", but an analytic profile at radius 0 is a sub-pixel spike of full height rather than nothing. Both layers therefore fade in over glowRadius in [0, GLOW_GATE_FADE_PX]. Measured against a fixed pixel width on purpose: gating against a sampleSpacing-derived floor would re-couple brightness to the rect size, which is the whole thing this design removes.

07 Arc gating

An arc is (start, length, intensity, hasStops), positions in perimeter fractions. Up to MAX_ARCS of them. Overlap resolves winner-take-all: the arc with the largest effective mask (coverage * intensity) owns both the colour and the emission at that point.

There are two different coverage functions, and conflating them is the classic bug in this file.

arcInsidearcCoverContinuous

Feedsthe hue average onlyfilament, halo and bloom

arcInside: hue crossfade only

Its feather sits outside the arc on each side, so a sample exactly at start or end still carries full weight in the hue average. The widths are asymmetric on purpose: one full sample on the head side, so adjacent samples' fade-in ranges are contiguous and a growing arc's leading hue hands over smoothly from one gather point to the next; a quarter sample on the tail side, near-hard, so the arc's own hue takes over immediately at its start rather than being averaged with whatever precedes it.

Wrap-awareness comes from testing both si and the virtual si + 1 and taking the max. When an arc extends past 1.0, a sample near position 0 is physically close to end through the perimeter loop, and the si + 1 test picks that up. The same expression handles the non-wrapping case, because si + 1 always falls outside a sub-unit arc there. Without it the hue breaks discontinuously at position 0 for any arc straddling the wrap point.

arcCoverContinuous: the visible extent

float cap    = length * ARC_FEATHER_MAX_SHARE;
float fH     = min(fHead, cap);
float fT     = min(fTail, cap);
float tailIn = smoothstep(0.0, fT, rel);
float headIn = 1.0 - smoothstep(length - fH, length, rel);
return tailIn * headIn;

The inward feather is the load-bearing choice. It means coverage is exactly 0 for any fragment whose perimeter position falls outside [start, start + length], which buys two properties: no bleed onto adjacent edges past a corner, regardless of width, and endpoints whose fade profile is a plain smoothstep in the perimeter parameter, so it reads the same shape whether the endpoint sits mid-edge or right at a corner. The trade-off is a visible inset: the arc lights at start + fT and ends at start + length - fH.

The cap exists because the feathers arrive as a fixed pixel span while length is a perimeter fraction. On a small rect a short arc can be narrower than the two ramps combined; they then overlap and clip the peak, so the same arc config renders dimmer on a smaller rect - measured at 0.21 versus 1.00 for length = 0.02 at 200x150 against 800x600. Capping each feather at a share of the arc's own length holds the peak at exactly 1.0 for any length at any size, giving a short arc a proportionally shorter ramp instead of a truncated top.

ARC_FEATHER_MAX_SHARE = 0.4 leaves a 0.2 * length plateau at full brightness between the two ramps. Up to 0.5 also holds the peak, but with no plateau the arc reads as a spike rather than a flat-topped segment. Arcs longer than (HEAD + TAIL) / 0.4 px never reach the cap, so the normal case is bit-identical to the uncapped version.

08 Travelling segments

A segment is (position, invSigma, boost, hasStops). Up to MAX_SEGMENT_BOOSTS. They are additive lights independent of arcs: they emit where no arc covers, and they deliberately bypass uIntensity so a segment stays lit on a darkened or fully dark arc.

Like arcs, the magnitude and the hue come from different places. The hue is gathered in the loop with the raw proximity weight g (not the arc-gated lg). The magnitude is evaluated pointwise:

float segCoverPt = 0.0;
for (int s = 0; s < uSegmentCount; s++) {
    vec4  seg = uSegments[s];
    float rel = sPos - seg.x;
    rel      -= floor(rel + 0.5);          // wrap to [-0.5, 0.5]
    float e   = rel * seg.y;
    segCoverPt += seg.z * exp(-e * e);     // boost * gaussian, summed
}

Summed rather than maxed, so overlapping segments reinforce. Left unclamped on purpose: a boost above 1 must still brighten. The separate emitCoverAll applies min(segCoverPt, 1.0), but that only bounds the shared halo and bloom reach and is not the segment's brightness.

Three gates come out of this, and they are not interchangeable:

NameExpressionApplied to
emitCovermax over arcs of (cover * intensity)the arc term in both filament and glow
emitCoverAllmax(emitCover, min(segCoverPt, 1))the segment term in the glow
filamentGatemax(smoothstep(0.5, 1, min(segCoverPt,1)), emitCover)the segment term in the filament

Composition then keeps the two sources' coverages separate:

vec3 arcCol   = col * uIntensity;
vec3 emitFil  = arcCol * emitCover + segCol * filamentGate;
vec3 emitGlow = arcCol * emitCover + segCol * emitCoverAll;
Why not one shared gate Summing the two sources first and applying a single gate let the segment's gate lift the arc term on a stretch no arc covers. A blue arc over half the ring plus a red segment on the other half rendered the segment magenta at roughly 2x brightness, and violet - arc-dominant - on its shoulders. With an arc covering, both emitFil and emitGlow reduce to exactly the old expression, so the common "tracer running along a lit arc" case is unchanged; only the paths where the two coverages disagree move.

09 The colour gather

The one remaining loop, and the only place a length is expressed as a perimeter fraction rather than in pixels. It produces colour only - never brightness, coverage or reach.

Per iteration

One UBO read, one subtract, one dot, one reciprocal, one gradient-LUT lookup, plus one exp() per active segment. No pow(), no in-shader stops walk, no HSV maths, and no fract() - the sweep advance is folded into the REPEAT-wrapped LUT coordinate.

vec2  dv = vPos - uLoopSamples[i].xy;
float dd = dot(dv, dv);
float g  = 1.0 / (dd + kc2);            // proximity weight
float lg = g * arcW;                    // arc-gated weight
acc     += baseColI * lg;
wsumLit += lg;

The kernel width, and why it is a fraction

float kc = max(peri * COLOR_BLEND_PERIM_FRAC, EMISSION_MIN_WIDTH);

The signal being filtered is the gradient LUT, which is itself parameterised by perimeter fraction: sample i contributes LUT(i / 128). A kernel measured in pixels therefore covers a different span of the gradient on every geometry, and the same colour stops render washed out on a small rect and crisp on a large one. Measured on the stock 4-stop ring, the colour sampled exactly on the red stop ran (0.95, 0.33, 0.06) at 200x150 against (0.96, 0.04, 0.00) at 2800x2200 - roughly 8x the hue bleed from geometry alone.

Two further properties fall out of the same choice:

  • A constant anti-bead margin. The kernel must stay at or above about one sample spacing or the blend collapses between samples. Spacing is perimeter / 128, so a perimeter fraction pins the ratio at COLOR_BLEND_PERIM_FRAC * 128 = 1.13 spacings on every geometry. The previous fixed 24 px span met that bound only up to a ~3000 px perimeter and was down to 0.31 spacings by 9900 px. (No beading was actually measurable there - a DFT of the hue around the perimeter put the 128-cycle component at the noise floor - because the gradient varies slowly over one spacing on a rect that large. The margin is a guarantee for dense colour stops, not a fix for an observed artifact.)
  • Renderer agreement. Both shaders derive the kernel from the same NEON_MAX_LOOP_SAMPLES-based fraction rather than from their own runtime sample count, so NeonOptimizedRenderer's numSamples slider does not move the colour blend. An earlier sampleSpacing-derived floor divided by the live count and landed 2x wider there.

0.0088 puts the kernel at 24.0 px on the stock 800x600 / radius 40 geometry, matching the previous fixed span, so default-sized output is unchanged. It is deliberately not coupled to glowRadius: the gather produces colour only, so a wide glow has no reason to desaturate the gradient, and the old max(glowRadius, floor) reintroduced exactly the pixel-space dependence this constant exists to remove.

Gated normalisation

vec3 col       = acc    / max(wsumLit,  WSUM_EPSILON);
vec3 segColHue = segAcc / max(wsumSegW, WSUM_EPSILON);

Dividing by the same weight the numerator was gathered with makes both a pure hue of unit magnitude everywhere on the quad: coverage and per-arc intensity cancel out of the ratio, and reach the emission solely through the pointwise coverages of sections 7 and 8.

Both used to divide by an ungated sum over every sample, so an unlit far side of the ring dragged the lit colour toward black by roughly kc / rectHeight. With kc pinned to a fixed pixel span that ratio grew as the rect shrank: a quarter-perimeter arc measured 0.79 of full brightness at 200x150 against 0.97 at 1920x1080. Gated normalisation is exactly 1.0 at every size.

Arc-local sampling is what makes hue rotation on an arc read as the gradient marching through the arc window rather than the arc's position sliding. A segment with its own stops samples row s of uSegmentLUT at clamp(0.5 + e * 0.5, 0, 1), which runs 0 at its head and 1 at its tail.

The colour cross-fade

Held entirely in the gradient bake and Update. On a stop change the renderer snapshots what is currently displayed as mLUTFrom, keeps the new bake as mLUTTarget, and blends toward it over colorTransitionDuration seconds, re-uploading mLUTDisplay each frame. Three paths:

  • First bake (!mHasBakedLUT): seed all three buffers and upload; there is nothing to fade from.
  • Duration <= 0: snap display to target, no fade.
  • Otherwise: fade from whatever is on screen, mid-fade or settled, so repeated changes chain smoothly rather than jumping back to the last settled ring.

Update drives it with raw frame time, not the animation clock, so a colour change still fades while animations are paused. The shader is not involved and cannot tell a fade is happening.

11 Quad sizing and fades

The margin setupGeometry

glowReach     = glowRadius * EARLY_OUT_RADIUS_FACTOR * (1 + bloomStrength * intensity)
filamentReach = max(lineWidth * 0.5, FILAMENT_MIN_HALF_WIDTH) * filSigmas
margin        = max(glowReach, filamentReach)
if (outsideCutoff.enable)
    margin    = min(margin, outsideCutoff.size + outSoft + 1)

The quad spans rect + margin on each axis, with sharp corners always. Geometry bounds the far region so there is no per-fragment discard, which is tiler-friendly.

glowRadius alone sizes the glow term. The old expression also carried a sampleSpacing * SPACING_FACTOR term, and since sampleSpacing is perimeter / 128 it won on any reasonably large rect at default glowRadius, making both the distance the bloom got truncated at and the brightness it still had there track the rect size: the fade began at 250 px on a 200x150 rect and 1542 px on a 1920x1080 one. It also asked for a roughly 5800x4900 px quad on a 1920x1080 rect. The bloom's reach is a function of glowRadius and nothing else.

The filamentReach floor is why lineWidth and filamentFalloff both appear in geometryDirty. Without it, glowRadius = 0 produced a zero margin: the quad landed exactly on the rect and clipped every exterior fragment, so the outside half of the filament vanished while the inside half stayed. The + 1 in the cutoff cap is a safety pixel so the shader's own soft mask fades to zero before the quad edge.

Keep in step Three places compute this expression: setupGeometry in neon-renderer.cpp, its copy in neon-optimized-renderer.cpp, and the reach line in both fragment shaders (for the bloom pedestal). They must agree or the pedestal lands at the wrong distance.

The quad-edge fade

float fadeFloor = uQuadMargin * QUAD_FADE_START_FRAC;
float cutEdge   = uOutsideCutoff + outSoft;
float fadeStart = (cutEdge < uQuadMargin) ? max(fadeFloor, cutEdge) : fadeFloor;
float dQuad     = sdRoundBox(vPos, halfSize + vec2(uQuadMargin), 0.0);
result *= 1.0 - smoothstep(-(uQuadMargin - fadeStart), 0.0, dQuad);

Measured per-axis via dQuad, not from the Euclidean d. What the fade hides is the quad, and the quad is a plain rectangle; keying on d put the ramp on a rounded contour that ate the corners early. At cornerRadius 0 on the stock 800x600 rect at cutoff 12, the band ran out to d = 16.97 at a corner while the d-keyed ramp was already zero by d = 14, erasing the outer ~30% of every corner - while black-rect.frag, drawn on a fullscreen quad with no fade, kept its square corner. With the cutoff disabled the same rounding chopped the bloom at d = uQuadMargin though the quad ran on to its own corner, so corners faded sooner than edges for no reason.

QUAD_FADE_START_FRAC is a fraction rather than a pixel span because the margin is proportional to glowRadius and so is the bloom profile it hides; a fixed ramp would vanish on a wide glow and dominate a narrow one. At stock glowRadius 5 / bloom 0.3 / intensity 1 the margin is 312 px, giving a 62 px ramp. Nothing derives 0.8 specifically.

The fadeStart floor handles the case where the margin was set by the cutoff instead of the glow. At cutoff 12 the margin is 13, so a bare 80% started the ramp at 10.4, inside the cutoff band, dimming its outer edge ahead of the cutoff mask - and only on the exterior, since the fade keys on positive d. Measured, the outermost band pixel sat at ~0.66 of its mirrored counterpart. Flooring the start at the cutoff boundary hands everything up to that point back to the cutoff smoothstep. The floor applies only when that boundary actually falls inside the quad, which keeps fadeStart < uQuadMargin always true - an inverted smoothstep is undefined in GLSL.

12 Sides, cutoffs, opaque fill

Early discard

if (dOut >  outSoft) discard;
if (dIn  < -inSoft ) discard;

Run immediately after d, before any filament or gather work, so a tightly cut band costs almost nothing outside itself.

The one-sided cut

if      (uGlowSide == GLOW_SIDE_INSIDE)  result *= smoothstep( softEdge, -softEdge, d);
else if (uGlowSide == GLOW_SIDE_OUTSIDE) result *= smoothstep(-softEdge,  softEdge, d);

Applied to the whole composed emission, after all three layers are summed, so it cuts filament and glow alike at the line. This is the single comparison against the sign of d that the SDF makes possible.

The cutoff masks

result *= smoothstep(-inSoft, inSoft, dIn);
result *= 1.0 - smoothstep(-outSoft, outSoft, dOut);

Symmetric around each boundary, so a sample exactly on the boundary sees about 50% weight. These are what let a wide glow be clipped to a stated band regardless of glowRadius.

The opaque fill black-rect.frag

An optional pass drawn before the neon, on a fullscreen quad with an identity MVP, so the effect can sit on its own background instead of only adding light. opaqueMode selects the region: NONE, INSIDE, OUTSIDE, BOTH (the band between the two cutoffs), or ALL (the whole viewport). It has its own analytic SDF anti-aliasing, which is why the fill lands cleanly on rounded corners at any softness.

In the optimized renderer this pass is drawn at full resolution, straight to the target framebuffer, and the half-res neon is composited over it. A hard-edged silhouette is the one part of the effect where a soft upscale would be visible.

13 Grading and output

Composition

vec3 result  = emitFil  * core  * FILAMENT_GAIN  * lineGate;
result      += emitGlow * halo  * HALO_GAIN      * glowGate;
result      += emitGlow * bloom * uBloomStrength * glowGate;

Hue-preserving Reinhard

float peak   = max(max(result.r, result.g), result.b);
float mapped = peak / (peak + TONE_MAP_SHOULDER);
result = result * (mapped / max(peak, 1e-6));

Tone-maps the peak channel and scales the others by the same ratio. A per-channel tone map desaturates warm mixes - orange drifts to peach - because red saturates while green and blue are still linear; scaling by the peak's compression preserves the original R:G:B ratio. With FILAMENT_GAIN at 12 the filament core is well past 1.0, so this is what turns a coloured curve into a white core with coloured edges.

Gamma and alpha

result = pow(result, vec3(GAMMA_EXPONENT));
float alpha = clamp(max(result.r, max(result.g, result.b)), 0.0, 1.0);
fragColor = vec4(result, alpha);

GAMMA_EXPONENT at 0.85 lifts the mid-tones so the falloff reads the way the eye expects. Coverage is the brightest channel: the hot filament core reaches alpha near 1 and occludes the background like a real glass tube, the dim halo and bloom stay near 0 and remain additive, and the dark surround at alpha 0 leaves the background untouched. Pairs with glBlendFunc(GL_ONE, GL_ONE_MINUS_SRC_ALPHA).

Premultiplication is also what makes the half-resolution path work at all: averaging two premultiplied pixels is correct, so plain bilinear filtering suffices and the blit is two statements with no dark fringing.

14 Half-resolution rules

The optimized shader is the same text plus a handful of unit corrections. Getting the rule wrong produces a geometric artifact rather than a crash, which makes it hard to trace.

What the CPU scales

Every geometric uniform is pre-multiplied by scale before upload, so the shader works entirely in FBO pixels and never learns the difference:

Scaled by scaleNot scaled
uRectSize, uCornerRadius, uLineWidth, uGlowRadius, uGlowSideSoftness, uInsideCutoff, uInsideCutoffSoftness, uOutsideCutoff, uOutsideCutoffSoftness, uQuadMargin, the loop sample positions uIntensity, uBloomStrength, uFilamentFalloff, arc and segment positions / lengths

The unscaled group divides cleanly: the first three are unitless multipliers, and the last are perimeter fractions in [0, 1], so they mean the same thing at any size.

This works because of a property of the SDF worth stating on its own: halve every input and the distance halves too. Every comparison in the shader is a ratio of two lengths, and both halve together, so every ratio is unchanged. The distance formula, the perimeter walk and all three brightness curves are therefore identical text in the two shaders.

What the shader must correct

A constant written into the shader cannot scale itself. uResolutionScale is uploaded purely so the shader can convert the baked pixel constants, and it is the only uniform in the pair that exists because of the optimization.

The rule: a constant measured in pixels needs the correction; a constant that is a plain fraction does not, because the value it multiplies is already in FBO pixels. COLOR_BLEND_PERIM_FRAC multiplies a peri that is already scaled, so correcting it would double-apply.

Miss one and the symptom is geometric. The arc feathers without their correction inset each arc's filament twice as deep as the full-res renderer does, leaving a visible stretch of bare halo past the ends.

The sample count

uNumSamples makes the gather loop bound dynamic, defaulting to 64 of the available 128. It changes one thing only: how many perimeter points the colour gather visits. It is safe to turn down precisely because of the section 6 rewrite - brightness, coverage and reach are all closed forms now and none of them touch the sample list. Halving the samples costs a little precision where two stops meet and nothing else: no dimming, no change in glow width, no beading.

Framebuffer discipline

const GLuint targetFbo = Framebuffer::GetBoundId();   // before pass 1
...
Framebuffer::BindId(targetFbo);                       // before pass 2

Restore the framebuffer the renderer was handed, never BindDefault(). During a frame capture the "backbuffer" is a real FBO, so binding the default one sends the composite to the window and the captured image comes back empty.

15 Droplets

Rain on glass in a band hugging the perimeter. It looks like a fluid simulation. It is a hashed grid masked by the same SDF, with an orientation-aware amplitude blend.

The band

depth = (INSIDE)  ? -sd - uBandOffset
      : (OUTSIDE) ?  sd - uBandOffset
      :              sd + bandWidth * 0.5 - uBandOffset;   // BOTH: straddle
across = depth / bandWidth;                                // 0 inner, 1 outer

Everything the droplet field does is parameterised on across. Which side the band occupies is taken from NeonConfig::glowSide, not its own setting, so rain and glow always share a side without being kept in sync by hand.

Two early exits carry most of this pass's savings: across < -0.25 || across > 1.25 discards before any droplet work, and a zero bandMask discards after the boundary feather. A thin band is a small slice of the viewport.

Cell size comes from the band

float lanes  = float(max(uLanes, 1));
float cellPx = bandWidth / lanes;
vec2  uv     = gl_FragCoord.xy / (CELL_UV * cellPx);

Originally the cells were sized from the viewport, so a 20 px band showed slivers of drops tens of pixels across - you saw fragments of enormous droplets, not small ones. Deriving cellPx from the band width instead means drops fit the band however thin it is, and lanes chooses how many sit side by side across it.

Gravity is global

Making droplets flow along the perimeter was tried and reads as a lava lamp rather than rain, so gravity points straight down the screen and the grid is hashed in screen space. Cells are 6:1 tall to leave room for each drop's trail; uv.y increases upward, so advancing the pattern along +uv.y makes drops travel down.

The band's orientation therefore has to be handled by amplitude, not by bending the grid. The outward normal comes from finite differences of the SDF:

float EdgeHorizontality(vec2 q) {
    vec2 d = abs(q) - uRectSize * 0.5 + uCornerRadius;
    if (d.x > 0.0 && d.y > 0.0) {
        return d.x / max(length(d), 1e-6);   // corner: normal is radial
    }
    return d.x > d.y ? 1.0 : 0.0;            // edge: whichever axis is further out
}
float runs = S(0.25, 0.8, EdgeHorizontality(q));   // 1 where the band is vertical

This was a finite difference of the SDF originally. At cornerRadius = 0 that difference straddles the corner's discontinuity and reports a direction wrong by up to 45 degrees - precisely where drops sit at a sharp corner. The analytic form is also two SDF evaluations cheaper per fragment.

runs then weights three layers. This changes amplitude only, never position, which is exactly why the grid never shears or tears at the corners.

Why the trickles are gated

A trickling drop occupies a cell 6 * cellPx tall. On a vertical run the band has hundreds of pixels to contain it. On a horizontal run the band is only bandWidth deep - at the defaults that is a 144 px cell seen through a 24 px slit - so all the band can show is a moving slice of a drop and a stripe of trail, with the drop's y sweeping ~130 px per cycle. That reads as rectangles with flat cut tops and bottoms, not as rain. Running the trickling layers at full strength there was the cause; trickle gates them down to a tenth on the horizontal runs and condensation carries the top and bottom instead.

Two things clean up what is left over:

  • The band feather widens with orientation. soft = clamp(mix(0.12, softPx, runs), 0.001, 0.5), where softPx = uGlowSideSoftness / bandWidth. A vertical run keeps the configured softness, since drops are sized to fit across the band and a crisp boundary is correct. A horizontal run softens it, so what overhangs fades instead of ending on a hard line. This also needs runs computed before the band mask. See why it stays small.
  • Trails taper toward both boundaries. c.y *= S(1.0, 0.55, abs(across * 2 - 1)). Trails run along the grid's tall axis and are the first thing a boundary chops, so they thin out before reaching it. Only the streak sheen is affected; drop bodies are untouched.

Per-drop fit, not per-pixel clipping

The two above soften the cut; they do not remove its cause. The band mask is applied per pixel at the end of the shader, so a drop whose centre sits near a boundary still has its far side multiplied away and reaches the screen as a half-moon or a cup - subtler than a rectangle, but still not a drop. Feathering harder only trades the artefact for a dimmer band.

The fix is to test the drop rather than the fragment. Every drop's centre is recoverable from the data the field already has, so DropLayer undoes the two shifts applied to uv.y and puts the centre back into pixels:

float dropBaseY = (id.y + dropY) / grid.y - (colShift + t * 0.75);
// wiggle re-evaluated at the DROP's y, not the fragment's, so the
// result is one value for the whole drop
float dwy = dropBaseY * 20.0;
float dropWiggle = sin(dwy + sin(dwy));
float dropX = (x0 + dropWiggle * (0.5 - abs(x0)) * (n.z - 0.5)) * 0.7;
vec2 dropUV = vec2((id.x + dropX + 0.5) / grid.x, dropBaseY);
float fit = DropFit(dropUV * uvToPx, 0.4 * uvToPx / grid.x, bandWidth);

Re-evaluating the wiggle at the drop's own y matters: x in the main body is a function of the fragment's baseUV.y (that is what makes the trail snake), so reusing it would make the fit vary across the drop - per-pixel clipping again, in a new disguise. uvToPx is threaded through Drops because it differs per layer: the finer layer is handed uv * 1.85 and so gets uvToPx / 1.85.

DropFit then measures the centre against the band and fades the drop whole:

float m = clamp(radiusPx / bandWidth, 0.0, 0.49);
return S(m * 0.6, m, across) * S(1.0 - m * 0.6, 1.0 - m, across);

A drop is at full strength once its centre clears its own radius from either boundary, and gone well before the centre reaches it. The gap between those two edges is where partly-overhanging drops live; the 0.6 keeps it narrow, because a wider window leaves them faintly visible as cups. m is clamped below 0.5 so the pair stays a well-formed window when the drop is wider than the band - which is the default, since lanes = 1 means "drops as wide as the band".

StaticDrops gets the same treatment, and needs it most: beads sit still, so a bead that overhangs is a permanent half-moon pinned to the boundary rather than one that drifts past.

The cost is one sdRoundBox per drop layer plus one for the beads, times the three Drops evaluations the height-field gradient needs - about nine extra SDF evaluations per fragment, all behind the early bail.

Keeping the drop round

Culling per drop only guarantees a whole drop reaches the band. It does not guarantee a round one, and the first tuning that used it produced circles with flat tops and bottoms - squircles sitting on the neon line.

The cause is the band feather eating inward from both boundaries while the drop occupies most of the band's depth. Work it through at the defaults. With lanes = 1 the bead radius was 0.353 in across units, so even a perfectly centred bead spans 0.147 to 0.853 - and a feather of 0.30 puts the mask at 0.36 where that bead's top and bottom sit. The drop is cut on both sides, symmetrically, which is exactly a flat-topped squircle. No amount of per-drop culling helps, because the drop being clipped is the one that fit best.

So the feather has an upper bound, and it is set by drop size relative to the band: it must stay inside the gap between a centred drop's edge and the boundary. Two changes bring the whole thing into range:

  • The horizontal feather drops to 0.12, well under that gap. It could be wide before only because it was the sole defence against slicing; with DropFit carrying that job, the feather goes back to doing what a feather is for.
  • The bead cell shrinks, from CELL_UV * 0.85 to CELL_UV * 1.3, taking the bead to about a quarter of the band's depth. A smaller bead relative to the band is rounder and denser: more of them clear DropFit's window instead of being culled, which is what pays back the density that culling costs.

The general rule, worth keeping in mind before changing any of these three numbers: drop radius, band feather and the fit window are one budget measured in across units. A drop must fit inside the band with room left over for the feather, or it gets clipped no matter how well it is culled.

That budget is also why trickle gates to zero on the horizontal runs rather than merely down. A trickling drop is 0.8 * cellPx across, which at lanes = 1 is 0.8 of the band's entire depth. It has no room for a feather and no room for a fit window, so on a horizontal run there is no amplitude at which it stops being a clipped squircle - only a faint one. Condensation carries those runs on its own.

The other box: a drop's own cell

Band geometry is not the only thing that can cut a drop square, and the second one is easy to misread as the first. StaticDrops wraps its coordinate with fract, so a bead is only ever evaluated inside its own cell - the neighbouring cells hash to different beads. Anything reaching past the cell boundary is simply not drawn, and the bead comes out flat-sided.

The offsets have to stay inside the cell for that not to happen. The bead's centre offset was (n.xy - 0.5) * 0.7, so up to 0.35 from the cell centre, against a radius of 0.3: 0.65 against the half-cell's 0.5. Off-centre beads were clipped, and raising the condensation weight made it obvious, because c = S(0.3, 1.0, c) in Drops fattens a bead well past its nominal radius at high weights. The offset is now * 0.38.

The tell that distinguishes the two: the band mask cuts along across only, so it can flatten a drop on one axis - a flat top and bottom, a cup, a half-moon. A drop flat on all four sides is its cell, not the band.

The trickling drops in DropLayer have the same problem and cannot be solved the same way. Their offset reaches 0.35 with a visible radius near 0.25 - the sum overruns the half-cell - but shrinking either one is not an option: the offset is the wiggle that makes trails snake, and the radius is the drop. So the column next door gets evaluated instead:

float side = stx < 0.0 ? -1.0 : 1.0;
vec2 own  = DropColumn(col,        stx,        ...);
vec2 next = DropColumn(col + side, stx - side, ...);
return max(own, next);

Two columns is exact, not an approximation: a drop spans less than a full cell, so a fragment can only be reached by its own column or by the one it is nearest to. max rather than a sum, because these are coverage masks and adding them would put a bright seam along the column boundary - trading one artefact for another. The per-column vertical phase (colShift = N(col)) means the neighbour has its own idy and sty, which is why the column body had to be split into DropColumn rather than sampled twice from the same locals.

The same cell holds a drop in y too, where the fix is free: the travel amplitude is 0.866 rather than 0.9, so the drop's y half-extent (0.4/6 of a cell) still clears the cell at both ends of its sweep. At 0.9 a drop was born and died against a flat edge as the cell above or below took over.

Cost is one extra DropColumn per layer. To see any of this, give the band a width far larger than the cell (bandWidth 4000 with lanes 125) so the whole field is unmasked on screen, and turn the neon off so it does not wash the drops out - cell seams are obvious there and nearly invisible inside a 24 px band, which is how they survived this long.

The third box: the orientation fade at a corner

The band mask and the cell are two per-fragment quantities that can cut a drop. runs is the third, and it bites hardest exactly where the other two are already hardest - at a sharp corner.

Around a corner the outward normal sweeps through a full 90 degrees, and S(0.25, 0.8, horizontality) completes its fade across about 38 of them. Twelve pixels out from the corner that is roughly 8 px of arc - narrower than a drop. Read per fragment, a drop straddling it gets a steep amplitude gradient across its own body, and since c = S(0.3, 1.0, c) is a threshold, that gradient becomes a hard radial edge: a crescent pinned to the corner. The condensation weight makes it worse, because mix(7.0, 0.5, runs) is a 14:1 ratio across those 8 px.

So the orientation weighting moved to the drop's centre, alongside the band fit - DropColumn multiplies by EdgeRuns(dropQ) and StaticDrops by mix(7.0, 0.5, EdgeRuns(beadQ)), and main keeps only the response to uAmount. One weight for the whole drop means the drop fades rather than being cut.

The single per-fragment use of the orientation that remains is the band feather, which is correct: the feather is a property of the boundary, not of any drop.

All three cuts share one shape of bug, worth stating once: any per-fragment quantity that varies faster than a drop is wide will cut that drop, because the mask is thresholded. Band depth, cell index and edge orientation were each read at the fragment; each is now read at the drop's own centre.

Water shading

Water has no pigment. A drop is legible only through what it does to the light around it, so the body stays about 90% transparent (bodyAlpha = c.x * 0.10) and two self-lit terms are drawn on top:

16 Lens flare

One fullscreen pass, no geometry. Every fragment works out its distance and angle from the sun and evaluates a stack of terms. Ported from a Shadertoy shader; see the licence note at the end of this section.

Where the sun is

Not in screen coordinates. The sun rides the perimeter at perimeterPosition, in the same 0-to-1 space the neon arcs use, with a signed perimeterOffset pushing it out or pulling it in. Crucially it follows the offset curve directly - itself a rounded rect of radius cornerRadius + offset - and the position advances by arc length along that curve, so the sun keeps a constant speed through the corners instead of visibly slowing. An offset below -cornerRadius clamps the corners square rather than inverting them. GetSunFragPosition is shared by both flare renderers so the sun lands identically; the half-res variant just multiplies the result by its scale.

Working space

vec2 uv    = gl_FragCoord.xy / uResolution - 0.5;   uv.x    *= aspect;
vec2 sunUV = uSunPos         / uResolution - 0.5;   sunUV.x *= aspect;

Aspect-corrected, y-up, origin at the screen centre. uFlareCenter arrives as normalised screen coords with y down, so it is converted: vec2((x - 0.5) * aspect, 0.5 - y).

Ghosts

Ten groups along the axis from the flare centre through the sun. Working relative to flareCentre re-anchors the whole cluster: dist 0 is the flare centre and dist ~ -1 is the sun, so uGhostOffset slides the group along that line - the -1.5 default biases them toward the border rather than the screen centre. uGhostSpacing stretches the placement axis without touching per-ghost colour or size.

Each group is three terms from circle(): a soft pow-based blob, a thin ring, and a flat-filled hexagonal sprite. The hexagon is not decorative - a real camera aperture is a ring of straight blades, and a ghost is an out-of-focus image of that opening.

hexCoverage builds the sprite's edge from the polygon distance with an fwidth-sized feather. The reference sliced it out with max(0.01 - regShape, 0) where regShape was a 0.5..0.51 smoothstep; that threshold lands at the flat bottom of the smoothstep, so the visible boundary was sub-pixel thin however wide the band was, and it aliased into stair-steps - worse in the half-res pass where a pixel spans twice the width. Coverage from the distance keeps the boundary about 1 px at whatever resolution the pass runs at.

Ghost colour is a procedural palette modulated by distance, so no two read the same, blended toward uGhostColor by uGhostTint when the rainbow is too much. Brightness still comes from the shape terms, so ghosts keep their falloff either way.

primarypow(abs(sin(a * N * 0.5)), 8) * lenModN thin countable spikes.
subpow(abs(cos(a * N * 0.5)), 20) * lenMod * 0.15Finer sparkle needles at the half-angles between primaries.
lenMod0.15 + 0.85 * hash(slot)Per-ray length scale. Applied to both layers so a short ray is short in all of them.

The random length is what stops it looking like a flower: without it every spike is the same length and the sunburst reads as a decoration rather than a light. Slots are indexed off mod(a, TWO_PI) so the hash is stable across rotation, and slot boundaries land at primary valleys where primary = 0, making the hash discontinuities invisible.

Core, haze, glow

float core = 0.1 / (pow(sDist * 5.0,  5.0)        + CORE_SOFT);   // 0.35
float haze = 0.1 / (pow(sDist * 10.0, 1.0 / 20.0) + HAZE_SOFT);   // 0.02
float glow = 0.1 / (pow(sDist * 4.0,  0.5)        + GLOW_SOFT);   // 0.10

The softening floors are the interesting part. Without them these are pure power laws, which are scale free: dividing the radius by uSize is algebraically identical to multiplying the whole term by uSize raised to a power, so size acted as a second, badly non-linear brightness knob - the core term scaled as uSize^5. A floor gives each falloff a finite peak, so size sets the radius and intensity sets the brightness, independently. The floor only bites near sDist = 0, so the far field and the reference look are unchanged, and it removes the divide-by-zero the reference had at the exact sun centre.

Note sDist = sunDist / uSize scales the core and haze, but the ray / 8.0 term has no distance falloff, so how far the rays reach is set by the global exp(1 - sunDist) / 5.0 envelope in unscaled units. That envelope is what keeps the flare from covering the whole screen.

The same class of bug, twice The flare's size-was-also-brightness problem and the neon's beading floor (section 6) are the same failure: a value that looked like one control was quietly acting as two, because a length had no intrinsic scale to be measured against.

Two charts. The first is what the CPU rebuilds and which GL object each rebuild writes; the second is the draw sequence one frame actually issues, for both the full-res and half-res renderers.

What rebuilds what

OnConfigChanged is where every CPU-side bake lives. It fires only when the composited config differs from last frame's, and each rebuild inside it is gated again on the exact fields it reads, so an animation moving one float does not re-upload four textures.

One frame's draw sequence

Both renderers are handed the same active config and the same bound framebuffer. What differs is where the neon lands and when the opaque fill is drawn relative to it.

19 GPU dataflow

The vertex shader, in full lib/shaders/neon.vert

precision highp float;

layout(location = 0) in vec2 aPos;

out vec2 vPos;

uniform mat4 uMVP;

void main() {
    vPos = aPos;
    gl_Position = uMVP * vec4(aPos, 0.0, 1.0);
}

That is the whole thing, and its brevity is the point. aPos arrives already in rect-local pixels - setupGeometry wrote the quad corners as +/-(halfSize + margin) - so passing it through untouched gives every fragment its own position in exactly the space the SDF wants. No inverse transform, no screen-space reconstruction, no resolution uniform in the distance path. uMVP is used only to put the quad on screen.

The same vertex shader backs black-rect.frag, neon-blit.frag and both debug overlays; the fill and blit passes simply bind an identity uMVP so vPos comes through as NDC.
