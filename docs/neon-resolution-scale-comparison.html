What resolutionScale does to the neon

Twelve scenes, each rendered at six values of NeonConfig::resolutionScale and compared pixel by pixel against its own 1.0 render. Every image here is a real 1280 x 720 frame from the library, captured offscreen. Below 1.0 the gather runs into a reduced buffer and a thin ring around the edge is re-shaded at full resolution (the edge ring, docs/neon-resolution-scale-plan.md step 5); every measurement is shown next to what the same scene read before that ring existed.

Regenerated on an Apple M2 Pro (2026-10-09), from the tree with the bloom's end fade and the output dither (V23 and R7 in review-findings.md): every image, error metric and timing below is that machine's, and neon-scale-check check measures drift from these 1.0 images - 0 on all twelve scenes there. Each image is the STEADY frame, the second after the config is set, which the hue-invariant field draws where it applies, within 1 level of drawing it directly. Every frame is dithered by +/- half a level, the same noise at every scale, so a reduced scale that agrees with 1.0 to within rounding still reads 1 here. Read the timing with that in mind. It is timed with the hue rotating, the library's default, and the fields now serve that frame below 1.0 as well as at it (I50-I58), so it costs about the same - 0.13-0.18 ms - at every scale on every scene but the smallest rect. A reduced scale saves time there, and, on any scene, on frames whose config itself animates (an intensity pulse, an arc wipe), which this page does not time. See docs/neon-reduced-scale-plan.md.

When the rect moves

A still frame hides one artefact. The reduced buffer's texel grid is fixed to the viewport, so as the rect slides the filament falls at different points between texels. Here the hairline scene's rect moves down 1/8 px per step and the dashed line is the true edge. Before the edge ring, low scales drifted off it and snapped back, and the line grew wider as the scale fell. The ring draws the filament at full resolution, so every scale now tracks the edge as 1.0 does; the grey figures under each strip are the old ones.

How this was measured

Capture

tools/neon-scale-check (see its README), linked against libedge-lighting.a twice: at the tree with V23 and R7 (one path at every scale since I57: the split gather, the reduced buffer and its blit, the edge ring, the glow coverage table and the hue-invariant fields) for every image and headline number, and at 542dad4, the last commit before docs/neon-resolution-scale-plan.md step 1, for every "before" figure. Hidden GLFW window for a GL 3.3 core context, the neon layer alone, drawn through OffscreenCapture at an explicit 1280 x 720 over a clear of rgb(5, 5, 8). Rect 640 x 360 at (320, 180) unless the scene says otherwise. For the images hueRotationRate and colorTransitionDuration are 0, the clock is ticked once and the second frame is captured, so every render is deterministic: three runs of each build agreed on every metric.

Scenes

The scenes are the ones the first version of this page used, on an Apple M2 Pro. Its harness was not kept, and its blurbs omitted every colour (and the overdrive's glow radius and the card's fill and glow), so each definition above was recovered by rendering it at 1.0 and matching that page's stored image: all twelve land within 1 level (2 on eight values), which is the variance between the two GPUs. Re-run on the pre-plan build, this harness reproduces that page's p99 within 1 level and its max within 2 in every scene at every scale. The definitions are tools/neon-scale-check/src/scenes.h.

Metrics

Per-pixel error is the largest of the three channel differences against the 1.0 render. Means and percentiles count only visibly lit pixels, meaning the brightest channel is more than 16 levels above the clear in either image, so the far bloom tail does not dilute them. PSNR is over the whole frame. "Light vs 1.0" is total Rec. 709 luma above the clear, as a ratio. The same definitions as the first version, checked by recomputing its numbers from its own images.

Grades

From p99 error: match 4 or less, minor 12 or less, visible 32 or less, severe above. The lowest-scale column is the lowest scale graded minor or better. The heatmap maps error 0 to 64+ levels onto its ramp, with differences of 1 level drawn black.

Timing and motion

GPU time is one machine (), so read ratios, not milliseconds, and expect another GPU to price the scaled path's fixed cost differently: an AMD Radeon Pro 5300M charges ~0.15 ms for the first offscreen pass of a frame, which this GPU charges ~6 us for (neon-perf-plan.md section 10.2). Timed with the hue rotating, for both builds: a still frame reuses its offscreen passes at every scale, so it costs a few hundredths of a millisecond whatever the scale and would show nothing about the knob. Each scale gets a freshly initialised effect; each figure is the minimum over three interleaved runs of both builds. The motion sweep moves geometry.position.y by 1/8 px for 64 steps. On the top edge's centre column it takes every row within 12 px of the true edge, subtracts that window's lowest luma, and reports the centroid of what is left minus the true edge, and the width at half its height. (The first version used no floor, which these numbers are not directly comparable with; its hairline wobble at 0.25, ±0.53 px, reproduces as ±0.53 here.)
